# deepWidgets decision and development review

28 November 2026 · `main` at `f158c36f14`

## Conclusion

deepWidgets grew around a legitimate prototype brief. Use the existing Cordis/Electron host to make desktop widgets feel real, prove that a local agent can operate and write one, and recover when generated code fails. The people and agents implementing that brief had sources, measurements, fault models and detailed acceptance checks. The repository kept updating those implementation facts. It never gave development and review agents a shared statement that the product should let people connect from compatible model-provider apps anywhere, with the PC owner governing the connection.

**The practical failure was at two levels.** At product level, the local prototype's assumptions remained in force as the app expanded. At merge level, at least one independently reproduced blocker went through without a public disposition or a corresponding fix on the reviewed branch. The record supports fixing both levels. It does not establish deliberate sabotage or commercial degradation.

This is the follow-up to the [architecture maps and first review](architecture.md). The [developer brief](../../specs/product-direction.md) contains the product direction you supplied and wording for the agent entrypoint.

## How the review was run

Three agents investigated in parallel. One reconstructed the decision history and considered the rejected designs. One designed backward from the remote product and checked the technical seams and provider assumptions. One audited how implementers and reviewers receive their briefs. I cross-checked their findings against the repository, the selected branch and worktree heads, the GitHub PR descriptions and discussion, and the timeline of merge and review events. Each agent received the remote product direction in its assignment.

## 1. Why the system took this shape

| Decision | Why it made sense at the time | What the new product changes |
| --- | --- | --- |
| **Fork DSH and trim its profile, October 24.** | Electron main, a child Node host, Cordis lifecycle and a renderer-side client already existed. The operator wanted to keep upstream code as a reference. The first tranche was deliberately a probe running through a genuine host/client round trip. Packaging, signing, updates, Windows/Linux and MCP were expressly outside that tranche. | Keep the fork and reusable lifecycle. Put a product-owned connector and platform release surface around them. A slim source checkout was never the objective. The effective shipped runtime and dependency closure now matter more than directory count. |
| **Use one shared runtime and one renderer per floating window, October 27–31.** | Cordis owned registration/disposal already. Sharing the action contract gave the UI and MCP the same semantics. A renderer per window kept a renderer crash local. The spike observed roughly 583 MB at 20 separate windows versus 198 MB in a shared layout. A shared renderer failure lost all of its windows. Those were prototype measurements. | Keep the shared action contract and renderer containment. Measure current memory, idle CPU and responsiveness before changing the process model. User controls, least-privilege grants and device availability need their own failure boundaries. |
| **Local stateless MCP and fixed tools, October 31.** | Loopback, browser-request rejection and a self-issued bearer fit the test environment. A stable tool list kept discovery small across widget counts. The stateless MCP handler avoided dependence on session state in the host. The explorers documented caller labels as provisional and recognized that a per-agent ACL had no trustworthy identity to bind to. | Keep compact discovery. Replace the remote meaning of identity and authorization. Distinguish a client grant, a widget installation, an operation and the connection carrying it. The stateless protocol decision survives this change. |
| **Crash-only host plus development gates, early November.** | One Cordis context preserved full plugin APIs and hot loading. Continuing after an uncaught exception was unsafe. A separate host or isolated per-widget process needed new routing, service brokers and promotion rules. Experiments showed test gates prevented many bad edits and crashes on the cooperative development workload. | Recovery and rollback remain valuable as availability features. Reopen the recorded single class of full-code widgets. Provide remote interaction with trusted widgets first. A later authoring tier needs OS-enforced limits in build and execution. |
| **Electron-owned MCP port, November 9.** | Moving the listener to Electron let a known endpoint survive a host crash. The PR separated pre-delivery unavailability from post-connect outcome uncertainty. It kept the loopback fence and served only HTTP on that listener. | Keep the stable ingress and outcome distinction. A remote grant, journal and emergency stop need to survive host replacement too. Endpoint continuity alone cannot preserve identity or exactly-once application of a retry. |
| **Screen first, gated modes, extensible pages, November 10–18.** | The operator chose to deliver a visible control panel first. Modes were discoverability and workflow controls. The plan made the approved-agent pane depend on consent, while the settings milestone deliberately shipped with a placeholder. Page authoring used the local full-Node trust premise. The operator accepted warnings for some build-fence findings. Per-widget origins and CSP were separately strengthened as actual renderer boundaries. | Keep the screen-first controls, and revise what they signify. A global or always-on mode is not consent. Preserve useful authoring as a separate capability. Put remote read, write, screenshot and window control under the appropriate grants. |
| **Shared widget kit and persistence in the existing runtime, November 18–28.** | Measurements favored the shared frozen kit over per-widget network installs. It avoided repeated downloads and duplicate React. The operator chose package lifecycle scripts with a denylist. For window records, the operator explicitly chose the existing `widgets` table over introducing another plugin and migrating Show/Hide. They specified that their changes win over agent defaults. | Keep offline page builds and preservation of operator choices. Decide separately which scripts can execute and how dependencies are tracked into deployed artifacts. Close the existing geometry authority problem before making those records persistent or exposing agent layout operations. |

It gave no reason for the deferral, an owner to restart work, or a condition that would reopen it. ## 2. Findings the first review missed or underweighted

### A reproduced window authority blocker crossed the merge

The November 26 adversarial review for #154 reported that widget content could move and resize its own locked window through a path outside the trusted bar. The reviewer demonstrated actual geometry changes even though the lock and resizable flags still reported the expected values. The PR merged November 28 with the same reviewed head. The checkout still has no corresponding renderer-to-native geometry guard. There was no fix or acceptance rationale in the accessible PR discussion. The review also reported a potential native hit-testing problem in which a widget's drag region can interfere with the trusted bar. That second observation was inferred and still needs a physical interaction test. [Window-bar PR](https://github.com/Ronitron007/deepWidgets/pull/154) · [Current window creation and event handling](../../../apps/desktop/src/deepwidgets-windows.ts#L255) · [Lock and resize rules](../../../docs/specs/window-manager.md#L78)

**Correction.** Make desktop main the only source of authorized geometry changes. Verify actual window bounds and physical bar interactions, including lock, resize, focus, mixed displays and the OS clamping a moved window. A property assertion that says Lock is on is insufficient. Resolve this before `wm.store` can persist a wrong value and before `wm.tools` or `wm.screenshot` extend window authority. Leave screenshots outside always-on Interact in the remote design. The current plan explicitly puts screenshots there. [Planned tool policy](../../../docs/specs/window-manager.md#L140)

### Packaging is a specific gap, with two independent prerequisites

The October blocker record says the normal package build likely omits the private `@deepwidgets/*` packages. Current source supports that inference. The release family still enumerates `packages/*/*` and `apps/*`. The CLI requires nine `@deepwidgets/*` workspace packages, and desktop preparation errors when a required local tarball is absent. The kit spec adds a separate issue after artifact preparation. Its installer links into core dependencies that are archived inside ASAR, while the inherited packaging policy strips declaration files needed by the kit's type check. I did not run a fresh packaging build. [Blocker record](../../../docs/blockers/problems.md#L14) · [Release family](../../../scripts/release/families.ts#L347) · [CLI dependencies](../../../apps/cli/package.json#L92) · [Package-closure rule](../../../apps/desktop/scripts/prepare-package-set.ts#L71) · [Packaged kit](../../../docs/specs/kit.md#L229)

**Correction.** Open a fork-owned packaging milestone. Qualify a clean install and upgrade without relying on the source checkout, first on the platform already backed by desktop evidence. Document which activities require the packaged kit and reproduce those too. Give the signed app, update feed, login item and packaged diagnostics fork-owned identities and checks. A source-run owner prototype can proceed alongside this. A pilot for other users needs the packaged result. Fewer upstream workflows were a deliberate fork decision, and hand-run checks do exist. PR #155 reports a successful full desktop suite on its revision. The current broad run's sandbox failures should not erase that evidence or the separate documented missing-workflow test issue. [Upstream resync kept workflow deletion](https://github.com/Ronitron007/deepWidgets/pull/73) · [PR #155 test report](https://github.com/Ronitron007/deepWidgets/pull/155) · [Documented test issue](../../../docs/blockers/problems.md#L11)

### The kit can undo a privacy policy already enforced in the root workspace

The root workspace explicitly blocks the `@openuidev/lang-core` install telemetry script. The separate kit workspace enables dependency build scripts generally. The kit spike encountered this telemetry script while exercising the strict default. The kit can therefore allow such a script if the dependency is pulled independently and the opt-out is absent. This is a conditional install-time egress and policy inconsistency. The review did not observe network traffic or disclosure of widget content. [Root lifecycle policy](../../../pnpm-workspace.yaml#L58) · [Kit spike](../../../docs/explore/widget-system/widget-kit-spike.md#L34) · [Generated kit policy](../../../deepwidgets/kit/src/folder.ts#L89) · [Kit process environment](../../../deepwidgets/kit/src/pnpm.ts#L38)

**Correction.** Apply the privacy policy to both install surfaces. Deny dependency scripts by default and explicitly approve the exact scripts genuinely needed. Test network behavior separately for clean startup, dependency changes, builds, updating and actual remote calls. Keep the 24-hour delay as one control for dependency resolution. The dependency's age cannot establish what its script is allowed to do.

### Runtime correctness evidence stops before the transport identity changes

The formal action model gives the jobs one caller/request key. The runtime has durable write marks and reports a lost result in some crash cases. The shipping MCP handshake issues a different caller each time. An ambiguous response and retry under a renewed credential therefore leave the model's assumptions. The first review identified the gap. Looking at the model explains why the replays and contracts could pass while the end-to-end behavior remains at risk. The generic `widget_call` also puts query and mutation underneath the same public tool description. Provider-side tool approvals cannot infer the real effect solely from that surface. [Action model](../../../.agents/skills/widget-state-models/action_contract/ActionContract.tla#L26) · [Current MCP action tool](../../../deepwidgets/mcp/src/index.ts#L928) · [Stable tool metadata and authorization](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

**Correction.** Distinguish read and mutation at the connector. Use durable operation IDs retained by the caller or gateway across transport retry, stable grants across credential renewals, and an outcome lookup. Filter discovery and results by grant and enforce it again at each invocation. Specify the limits. A provider making a fresh call without the same operation identity is making a new request. Test a committed write with a lost reply, app restart and credential renewal in one scenario.

## 3. How the product direction fell out of agent context

The repo requires every agent to read the root `CLAUDE.md`, and the root `AGENTS.md` points to it. The goal in that file is still a floating desktop widget whose plugins run on Cordis. The README describes the local product. In an inspection of 68 registered worktrees, 66 committed roots contained the same floating-widget goal, one contained an older goal, and one had no root `CLAUDE.md`. These are registered worktrees and committed files. They do not identify which agents were active or what they privately knew. [Agent entrypoint](../../../CLAUDE.md#L3) · [Cross-tool pointer](../../../AGENTS.md#L4) · [Local product README](../../../README.md#L19)

There is a working mechanism for maintaining facts about `main`. PR #101 explicitly updated the root map, port behavior and checks against the code. The Claude hook fires around Bash commits and tells the agent to keep those facts current. It neither seeds a new task with product direction nor updates files or prompt context in an older worktree. Recent implementers had plan rows with precise commands, failure cases and mutants. The checked-in task files are from the earlier fork/probe/trace work. The broader handoff protocol is explicitly proposed and no checks manifests were found in the reviewed tree. The historical handoff study attributed 20 of 28 failures to sender content and three to receivers skipping a step. That is another reason to improve the brief itself. [Head housekeeping](https://github.com/Ronitron007/deepWidgets/pull/101) · [Claude hook configuration](../../../.claude/settings.json#L3) · [What the hook does](../../../.claude/hooks/head-node-reminder.sh#L34) · [Proposed handoff](../../../docs/specs/handoff.md#L3) · [Handoff evidence](../../../docs/specs/handoff-evidence.md#L3)

Good unit review did happen. The agent-library reviews tightened validation, the kit reviews added cross-process coordination, and #157 changed the spec before #156 landed the fixes. #154 shows the weak link. An issue comment could correctly identify an operator-authority violation and still provide no visible merge disposition. The window plan invokes the MVP process, which says an independent review must have no open findings before merge. Compare #154 with #107, where the maintainers recorded the specific open findings and the operator’s reason for accepting them, and with #155, where a follow-up linked the blocker to its fix and checks. That distinction matters more than the number of reviews. [Kit review follow-up](https://github.com/Ronitron007/deepWidgets/pull/142) · [Spec correction before implementation](https://github.com/Ronitron007/deepWidgets/pull/157) · [Window-bar merge](https://github.com/Ronitron007/deepWidgets/pull/154) · [Merge rule](../../../docs/plans/widget-mvp.md#L3) · [Recorded acceptance](https://github.com/Ronitron007/deepWidgets/pull/107#issuecomment-6852725741) · [Recorded fix and verification](https://github.com/Ronitron007/deepWidgets/pull/155#issuecomment-7188213048)

**Correction to the workflow.** Put one owner-supplied product statement in a tracked file and a short pointer under `head.what`. For a new or resumed task that changes trust, action behavior, data, windows, packaging or startup, the sender gives the unit, worktree/base, and product direction revision. The receiver names the one relevant product rule. The reviewer checks that rule against the actual change, and any known blocker gets either a fix with evidence at the merge SHA or an explicit owner decision with a contained scope and a condition that reopens it. For older worktrees, let agents read the canonical revision without rebasing or changing in-progress files. For agents already in flight, a new merge alone cannot transmit a new brief. A handoff at the next natural checkpoint does that. [Product direction](../../specs/product-direction.md)

## 4. Recommended order of decisions

1. **Record the product direction in the repository and distribute its revision.** Make the agent entrypoint explain “compatible provider apps, selected PC, operator-granted widget access.” Describe the local endpoint as the current development surface. Add a remote product milestone with scope and acceptance to make the objective visible in task and review briefs. Let existing purely local units finish within their scope. Pause expansion of remote privileges until their design is explicit.
2. **Fix the current authority regression and disposition it publicly in the project record.** Verify actual widget window bounds on the reviewed artifact. Review whether the current modes should fail open in trusted developer mode or change sooner. Scope any accepted exception to the relevant local lane. Open the packaging work in parallel.
3. **Build a narrowly scoped device broker and connector.** Keep permission and durable audit in a trusted PC component that remains usable during widget-host failure. Use the same widget action contract via local and outbound paths. A relay can route requests, while the PC decides which grant applies. Expose one trusted bundled widget's read and one useful mutation. Keep authoring, packages, remote layout and screenshots out of this slice. A hosted connector plus an independent MCP client is an initial compatibility test. A second hosted vendor using the same device policy is the threshold for a provider-neutral hosted claim.
4. **Qualify failure, privacy, and platform behavior.** The operator can revoke during host restart, no queued write runs after sleep, an interrupted mutation can be reconciled, data and device routing stay isolated, and local widgets keep working with the relay offline. A clean packaged profile can support those scenarios. Make relay payload visibility explicit. OpenAI's private tunnel can be an adapter for supported OpenAI apps. Claude's hosted connector originates in Anthropic's cloud and has different reachability requirements. The shared contract remains MCP and the shared permission model remains device-owned. [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) · [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) · [Claude custom connector network requirements](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
5. **Decide advanced authoring in its own design.** Explicitly revisit the old single class of full-code widgets. Preserve unrestricted Cordis authoring as an operator-trusted developer option if desired. Require isolated build and execution, controlled dependency scripts, coherent host/page promotion and versioned permissions before a remote authoring feature. Decide whether any remote screenshots or layout operations are worth the added authority and design them separately.
