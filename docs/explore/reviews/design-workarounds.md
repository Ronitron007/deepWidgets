# deepWidgets design workarounds review

28 November 2026

## The pattern

The worst workarounds protect one step while leaving the thing the user cares about without an owner. The port file has an owner. The widget store can still have two writers. An install has a commit point for the plugin row. The page and the state it consumes can belong to another revision. The watchdog can tell Electron which widget probably stalled a host. That widget still takes the whole host down. These are different defects with the same design lesson. Decide which component owns the invariant, then give adapters and recovery logic a smaller job.

I reviewed the runtime at the window-bar merge and checked the newer decisions on GitHub. The newer changes were documentation only at the time of review. The window plan now records the geometry-authority finding as open. A separate owner decision defers the known permission gaps to one permission-layer design. That supersedes my earlier reading that the project had no recorded disposition for those gaps. The proposed fixes below respect that choice. [Window-plan update](https://github.com/Ronitron007/deepWidgets/commit/839d6e2692c67e5a24027279136f8ae4e4e40cce) · [Permission-layer decision](https://github.com/Ronitron007/deepWidgets/commit/8809c327e3475156d8f4dd4519bb4d46611a1a7e)

## 1. The store has no single writer

**Workaround.** Atomic file replacement, in-process serialization, a discovery-file owner and a separate kit lock each solve a narrower problem. None gives one writer authority over the widget store. The supported development topology allows a desktop and a CLI host in the same `DSH_HOME`. The existing smoke even starts a second host against the same home, and asserts that it does not replace the first host's port file. The second host can keep running. Widget artifacts are per profile, but widget state, program, operation receipts, window visibility and the committed-bundle map are rooted in the home. The JSON backend's default layout is a whole-domain snapshot with no cross-process write lock. [Kit's stated topology](../../specs/kit.md#the-lock-kitservicelock) · [Existing same-home smoke](../../../tools/widgets-mcp-port.mjs#L326) · [Storage configuration](../../../packages/bundle/base/cordis.patch.yml#L175) · [JSON backend limits](../../../packages/storage/storage-json/README.md#known-limitations-and-deferred-work) · [Widget domain](../../../deepwidgets/widgets/src/index.ts#L340)

**Failure chain.** Two hosts load the same durable snapshot. One records a user's Hide choice. The other makes an unrelated widget write using the snapshot it loaded earlier. Each can report a successful durable write. Restart can reveal the last writer's snapshot and lose the Hide choice, a state update or a receipt. Different slugs do not prevent the loss because both live in the same file. If a receipt is lost, a retry problem can follow even after fixing connector identity. This is a static inference from the writer model. The discovery test checks a different resource.

**Correction.** Keep JSON for the first slice if it is adequate. Enforce one writer per durable widget store **before it opens**, and give every process that needs the data access through that owner. A second development profile can use an isolated store or explicitly attach to the first owner. If simultaneous writers become a real requirement, move to transactionally coordinated state with profile and installation identities. Another file lock around the final rename still permits a stale read-modify-write. **Decisive check:** start two hosts against one store. Either the second cannot write, or both independent changes and their receipts survive restart and agree in both hosts.

## 2. Turn off and Hide describe what happened, then try to remember what the user wanted

**Workaround.** Turn off changes Loader rows first and writes the durable disabled-slug record afterward. A later install consults that record. A failed write, interrupted change or multi-row error can leave effective workload state and operator intent out of sync. The installer contains further reconciliation for stale row overrides, including a warning for a case where a replacement that should be off has already started. Hide has the complementary issue. A missing visibility record and an unreadable store both become `shown: true`. The window event stream can publish that answer even when the storage domain failed to open. Electron treats it as an instruction and can show the window, while the same failure prevents the Hide action from persisting a correction. [Turn off ordering and row reconciliation](../../../deepwidgets/mcp/src/creation.ts#L831) · [Replacement warning](../../../deepwidgets/mcp/src/creation.ts#L1084) · [Visibility default](../../../deepwidgets/widgets/src/index.ts#L951) · [Window stream baseline](../../../deepwidgets/widgets/src/index.ts#L1660) · [Desktop window sync](../../../apps/desktop/src/deepwidgets-windows.ts#L234)

**Correction.** Store desired state under a stable widget installation ID before acting on it. Use reconciled effective states such as pending, applied, blocked and unknown. An unreadable preference is an explicit unknown. Preserve the last known Hide when available and use a conservative recovery state on cold start. An unavailable widget store must leave the core operator UI usable. Keep Hide, stop execution and pause remote access distinct. **Decisive check:** interrupt a Turn off after the preference is accepted, restart, and then replace the widget. It remains off. Corrupt or deny access to the state store after a Hide and confirm that a restart does not silently show the widget.

## 3. An install commits a package name before it commits a usable widget revision

**Workaround.** The installer alternates names to work around the Loader's package identity rules. It promotes standby on registration, switches the committed name, removes the old bundle and later switches the page link. The runtime announces a widget while its seed write is still pending. Registration within the wait budget therefore stands in for verified readiness. The page link is selected separately and can fail after the host has already switched. An atomic rename gives each individual lookup a complete link. A renderer document still makes multiple requests under a stable slug URL, and the asset handler can resolve that link again on each request. An older page can therefore see newer assets or a missing asset during activation. [Package promotion and link update](../../../deepwidgets/mcp/src/creation.ts#L1042) · [Runtime registration and seed](../../../deepwidgets/widgets/src/index.ts#L1560) · [Page lookup](../../../apps/desktop/src/deepwidgets-windows.ts#L137)

**Failure chain.** A new handler and page pass the test run against initial-state fixtures. Existing state is retained by slug and can have a shape the new handler never checked. The candidate registers. The previous activation is retired while state seeding is still unresolved. After a failed seed, incompatible persisted state, link error or interrupted activation, the user can have a new handler with an old page, a page whose assets change underneath it, or a widget listed as live that cannot answer. The renderer's two-failure fallback to the shared shell may show an error for a widget with a custom catalog. That is an error view, with useful value as recovery UI. It cannot substitute for a compatible last-known-good revision. [Build and test gates](../../../deepwidgets/mcp/src/creation.ts#L399) · [Retained state and seeding](../../../deepwidgets/widgets/src/index.ts#L1395) · [Fallback](../../../apps/desktop/src/deepwidgets-windows.ts#L355) · [Catalog check](../../../deepwidgets/widget-kit/src/index.tsx#L135)

**Correction.** Give each immutable widget revision a single descriptor containing the host payload, exact page digest, action contract, data compatibility or migration, and build inputs. Prepare it before publishing. Use a single durable activation decision and generation-addressed assets. Bind actions to the generation the client observed or require refresh. Commit after checking current persisted data and readiness, or reject the upgrade if it cannot migrate. Keep one complete previous usable generation through activation and treat rollback after data migration as an explicit compatibility decision. **Decisive check:** interrupt every durable activation stage, test a candidate against real previous-version data, and hold open an old page while deploying. Readers see coherent generations or a typed superseded state.

## 4. The artifact key and the lockfile describe less than the build actually used

**Workaround.** The page build hashes source files and a kit version number. An app update can retarget the kit's core links without changing that number. The builder can render-check freshly built bytes, then discard them and reuse older bytes if the path already exists. Also, the installer borrows dependency paths from the current kit without a reader lease. The kit retains the latest three editions without consulting in-flight builds. The single shared kit and offline build are sensible. The weak identity and lifetime are the problem. [Page key and reuse](../../../deepwidgets/mcp/src/page-gate.ts#L201) · [Reuse after render validation](../../../deepwidgets/mcp/src/page-gate.ts#L392) · [Core links](../../specs/kit.md#the-kit-folder-kitfolder) · [Kit retention and dependency paths](../../../deepwidgets/kit/src/index.ts#L428)

**Correction.** Pin immutable build inputs for a build or widget generation. Make the artifact identity include resolved core and extras, the toolchain and the produced digest. Publish the exact bytes the checks tested. Reclaim inputs when no active or retained revision or in-flight build references them. Keep the kit's fail-fast behavior under contention if useful. **Decisive check:** change only app-bundled core packages, rebuild identical page source, and verify the installed digest matches the checked output. Pause a build while creating enough kit updates to pass the retention cutoff and verify that its original inputs remain usable.

## 5. Quit and update ask the old app what work is running

**Workaround.** deepWidgets inherits DSH's desktop updater and Quit flow. Their inspectors require Agent and Jobs services that the default trimmed profile disables. Thus the ordinary Quit path can report unknown activity even when idle. If the inherited updater reaches its install preparation in that composition, the activity inspection can refuse before it gets to the handoff. Its lock listens to the Connection HTTP path. Widget MCP uses its own route, and widget timers start in process. The meaningful promise is “no new work can begin while we drain,” beyond whether a particular HTTP prefix is closed. [Trim](../../../deepwidgets/trim/cordis.patch.yml#L465) · [Quit inspection](../../../apps/desktop-host/src/quit-inspection.ts#L23) · [Update work check](../../../apps/desktop-host/src/update-tasks.ts#L28) · [Connection admission](../../../packages/client/connection/src/index.ts#L146) · [MCP registration](../../../deepwidgets/mcp/src/index.ts#L1167) · [Desktop installer handoff](../../../apps/desktop/src/main.ts#L774)

**Correction.** Have a single owner track widget actions, timers, install promotions and kit changes as operations. Close admission there, drain or cancel admitted operations according to their actual effects, and close subscriptions separately. Keep lifecycle ownership with the desktop coordinator and record which host generation can accept work. Preserve distinct outcomes for committed, cancelled, and genuinely unknown operations. Keep the existing supervisor disarm as protection until a real handoff replaces it. **Decisive check:** use a real trimmed desktop, sustain live read streams, start work through UI, MCP and timers, and run the stop/update path. All entry points agree on the fence and the user sees a truthful result. This is a design trace, not a claim that a packaged update ran in this review.

## 6. The watchdog keeps the host recoverable while widgets still share its failure domain

**Workaround.** The shared host attributes crashes with row context, a synchronous running slot, a heartbeat, optional native-stack evidence, time-limited disposers and quarantine. This is valuable recovery work. It also assigns several meanings to a single heartbeat and tries to stop newly admitted side effects after code has run. A slow machine, a failed plugin, a blocked storage operation and a slow authority action all present as delayed progress. HMR disposal can stop waiting for cleanup while the executing code still has OS authority. The safe-host spec mentions a five-second exclusive transaction limit, and the deferral record says that limit is unimplemented. An asynchronous stall can block progress while the event loop remains healthy. [Watchdog and disposer design](../../specs/safe-host.md#watchdog-rule-safe_hostwatchdog) · [Deferred HMR limit](../widget-system/where-we-stand.md#deferred-by-the-operator-standingdeferred) · [Original alternatives](../widget-system/options.md#fault-isolation-optionsisolation)

**Correction.** Keep watchdogs, timeouts and load diagnostics. Put remote-capable authored work in an execution mode with a bounded lifecycle and brokered effects. Fatal or unresponsive work then stops locally, while the control UI, durable operations and other widgets continue. For the first remote pilot, trusted bundled widgets can be a simpler baseline. If a trusted runtime wedges, recovery still needs a clear generation and an independently usable pause control. **Decisive check:** run one widget that fails to settle and compare it with a known slow but progressing host. An affected execution unit is contained, other widgets remain responsive, and operator controls remain available.

## 7. The operator panel reuses the machinery it must be able to recover

**Workaround.** The tray opens a built-in widget that talks through the same widget runtime. Special watchdog attribution for its privileged calls, synthetic refresh events, shorter login-item subtimeouts and a nonwaiting kit snapshot keep different pieces from blocking it. The kit polling fix was justified. A lock could otherwise time out all Settings. But the owner mechanism should not depend on the widget data domain or on a compound Settings query completing. [Main widget registration](../../../deepwidgets/widget-main/src/index.ts#L579) · [Settings composition](../../../deepwidgets/widget-main/src/index.ts#L490) · [Kit lock effect on Settings](../../specs/kit.md#decisions-kitpanedecisions) · [Native menu controls](../../../apps/desktop/src/deepwidgets-menu-bar.ts#L71)

**Correction.** Give desktop main a minimal native or trusted recovery surface with typed administrative state. Let it display host health, stop remote admission, hide windows and expose an actionable recovery reason when the widget runtime is unavailable. The normal panel can still use the shared UI components. It can show stale snapshots with an explicit state and refresh each independent subsystem separately. The geometry policy belongs to the native window owner. Persistence and hosted window tools should depend on verified owner control of actual bounds. **Decisive check:** fail storage, restart the worker and hold the kit lock, each independently. Pause and recovery controls remain usable and show which subsystem is affected.

## 8. Retry and refresh compensate for the absence of a shared operation and observation protocol

**Workaround.** The local UI avoids retrying mutations to reduce duplicates, but sends no operation ID and turns structured failure into display text. The MCP guide asks a model to pass an ID. The server keys it to a transport-issued caller and checks the *current* action schema before looking up any receipt. Even with a stable caller, after a deployment removes or changes that action, a retry can return an action or validation error before reaching a receipt for the earlier commit. Separately, the widget view loads its initial program independently of subscribing. A first stream baseline can advertise a newer program than the one fetched, but the first baseline only refetches when the initial request failed. Later baseline events can compare against the advertised revision rather than the revision actually applied. [Local channel](../../../deepwidgets/widget-kit/src/channel.ts#L82) · [Action and receipt ordering](../../../deepwidgets/widgets/src/index.ts#L1209) · [Initial program and stream](../../../deepwidgets/widget-kit/src/index.tsx#L119)

**Correction.** Give each UI or connector operation a stable identity before dispatch. Store and authorize its outcome independently of resolving the current action table. Version new operations against the intended revision and define whether an interrupted effect is unknown or committed. For observations, start from a versioned snapshot and reconcile from the client's last applied revision, including the first stream baseline and host-generation change. Polling by cursor is fine for compatible clients. An audit journal and a view refresh serve different purposes. **Decisive check:** drop the response after commit, activate a new widget revision, then look up the old receipt through both UI and MCP. Separately, change the program between the first fetch and subscription and verify the view converges even with no further update.

## 9. The network fence and feature flags cannot provide end-to-end permission

The original loopback fence and nonce check fit a local development interface. Global modes, hidden tool names, a TypeScript-only plugin facade and install validation can help cooperating authors. They cannot decide what untrusted code may do on the PC. The latest project decision explicitly groups these gaps into one permission layer and rejects partial guards that could suggest protection already exists. [Latest permission-gap decision](https://github.com/Ronitron007/deepWidgets/commit/8809c327e3475156d8f4dd4519bb4d46611a1a7e) · [Local MCP modes](../../specs/modes.md) · [Product direction](../../specs/product-direction.md)

The durable correction has two sides. A trusted broker authorizes discovery, disclosure and each effect using a revocable grant that identifies the PC, principal, widget installation and permitted operation. An authored widget executes in a process that receives only the effects its policy permits. Public MCP speaks only to the former. Extend the architecture to authoring once the permission design supports it. The first pilot can run trusted bundled actions while exercising denial, revoke, restart and retry. A provider prompt or hosted tunnel can complement the design. The PC owner remains the authority.

## 10. The fork's trim is doing the work of a product composition and release model

Using a subtractive overlay was the quickest way to retain the DSH reference tree and get the probe running. Over time the desktop has inherited a full product boot and then covered incompatible requirements one by one. The hidden DSH window retained for checks, wrong activity providers on quit, and the mismatch between local workspace membership and packaged release membership are related consequences. A first-party widget can thus work in a source checkout while the packaging closure omits its tarball and the packaged kit lacks its expected core declaration files. [Fork trim and original scope](../../specs/fork-trim.md) · [Hidden window rationale](../../specs/main-widget.md#provisional-choices-main_widgetprovisional) · [Release family](../../../scripts/release/families.ts#L347) · [Packaged kit prerequisite](../../specs/kit.md#open-points-kitopen)

Keep the upstream source and reusable Cordis packages. Define a small explicit deepWidgets composition with required startup capabilities, and drive package closure and startup/quit/update checks from it. The existing source profile remains useful for development. Qualify an installed artifact from an empty machine account and upgrade a prior profile. A database migration, provider adapter or rewrite of the upstream tree is not necessary to start that work.

## Order and trade-offs

The [current product direction](../../specs/product-direction.md) puts a local temporary surface and decision loop first. That pilot can use built-in controls and trusted handlers. The prerequisites below apply as it adds durable state, new capabilities, or hosted access.

| Priority | Correct this | Keep |
| --- | --- | --- |
| Before expanding local or remote scope | Own the widget store, preserve owner intent on failure, and agree on the complete permission design. Establish the agent-facing product direction. | Atomic writes and local development tooling. |
| Before a hosted pilot | Publish whole widget revisions and stable operation receipts. Make pause/revoke independently operable. Qualify real quit/update admission and a clean packaged build in parallel. | One shared action contract, per-widget renderer isolation, the stable loopback listener, watchdog recovery and the explicit unknown outcome. |
| Before hosted authoring or broader window control | Isolate build and execution, tie permissions to widget identity, and prove trusted native window and data boundaries. | The editor experience, offline kit and owner-first placement. |
| After measuring actual demand | Decide whether multiple writer profiles, durable subscriptions, automatic side-effect reconciliation and additional platform distributions are worth their complexity. | Cursor polling and one writer can keep the first release small. |

The decisive tests should cross two seams each. A unit mutant can show that a flag works. A combined test shows that a stopped host, a lost reply, a changed revision or a damaged record cannot reverse the user's decision. Start with same-home writer ownership, the real owner control path, and a coherent activation under failure. Those tests challenge the current architecture directly.

## Evidence

Three independent investigations returned findings on lifecycle, artifacts and state, and desktop/connector behavior. I checked the cited paths and integrated them with a direct review of the connector, profile, release and GitHub decisions. The focused desktop suite ran **225 passed, 1 skipped across 9 files** on the unchanged runtime tree. The cross-process and ordering scenarios above are source-based inferences unless attributed to an existing test or prior review. No runtime changes, live provider pairings, packaged update, or new security probes were performed.
