# Shared widget interactions and Vercel UI SDK

**Recommendation.** Define the interaction conventions in deepWidgets and apply them to both the built-in shell and authored pages. Keep Vercel Labs UI SDK as a candidate implementation for individual controls. Start by making the existing controls and frame consistent. The dependency decision follows a comparison in the packaged desktop app.

## Where uniformity comes from

The built-in shell uses the `shadcn-widgets@1` OpenUI catalog and exports reusable controls for authored pages. The page template already uses the common runtime from `@deepwidgets/widget-kit`, and its example catalog extends the default. The shell and authored pages have separate CSS entry points that repeat the same theme mapping. The renderer core already provides loading, empty, removed, and page-error views. Those shared pieces give deepWidgets a way to improve many widgets together. The two entry points can keep their own build layers and import one shared token mapping. [Default catalog](../../../deepwidgets/shell/src/library.tsx) · [Shell stylesheet](../../../deepwidgets/shell/src/styles.css) · [Authored-page stylesheet](../../../deepwidgets/shell/page.css) · [Renderer core](../../../deepwidgets/widget-kit/src/index.tsx) · [Page template and catalog](../../specs/agent-library.md#the-catalog-of-a-page-agent_libraryguidecatalog)

| Owner | Proposed responsibility |
| --- | --- |
| `@deepwidgets/shell` | Own color, contrast, spacing, focus styles, shared controls, and their OpenUI bindings. Bring reusable interaction behavior into the existing wrappers so both the default catalog and custom pages can use it. Preserve existing catalog behavior and version any incompatible change. |
| `@deepwidgets/widget-kit` | Own the common page frame, connection and recovery states, and how a control receives action status. Give custom pages the same status and action bindings while allowing a different layout and catalog. |
| `@deepwidgets/kit` | Deliver and pin the approved packages for authored pages with the existing single React instance. If a shell control adopts UI SDK, bundle the pinned SDK as a shell dependency. Add it to the public kit Core list only if deepWidgets decides to support direct imports by widget authors. |
| Widget host and Electron main | The widget host owns action execution and its outcomes. The device permission design owns remote access. Electron main protects the operator's window controls and manages the floating window separately from page content. |

At the control, a person can reach it with the keyboard, identify what it does with a screen reader, and return to a useful focus position after working in a popup or closing it with Escape. It fits a compact window and follows the app theme. At the frame, distinguish first load, empty data, disconnection, a write in progress, a write that completed, a known failure, and an outcome the app cannot yet determine. Show feedback where the person acted. Keep the page responsive while preventing an accidental repeat of a pending write on the same target. The host reports the durable outcome. Use the same action semantics for a local control and a permitted MCP call. [Shared action design](../widget-system/where-we-stand.md#the-seam-standingdesignseam) · [Native window bar](../../specs/window-manager.md#the-bar-window_managerbar)

For example, when someone checks an item in Grocery, the checkbox shows the pending operation while the host saves it. After confirmation, the item remains checked when the widget refreshes. If the reply is lost after dispatch, show that the outcome is unknown and reconcile with the host before offering another write. A permitted agent uses the same named mutation through MCP. The desktop reflects the resulting state without moving keyboard focus, and the action can run while its widget window is closed.

Today the checkbox dispatches the action and reads its value back from the widget. The renderer does not send a request ID, and the channel currently presents loss of the host response as a generic action error. A consistent pending or unknown state requires the shared action channel to preserve operation identity and the host's outcome. Replacing the checkbox alone leaves that gap. ## What Vercel supplies

Vercel Labs launched UI SDK as a public beta on November 12, 2026. It is a headless component library with a framework-independent core and framework adapters. It provides behavior for controls such as menus and selects, including focus, keyboard navigation, selection, dismissal, and accessibility. The deepWidgets shell would still supply the styling, catalog, and action bindings. Its current wrappers already use primitives such as Radix, so a replacement needs to improve an observed interaction. [Vercel launch](https://ui-sdk.dev/docs/core/changelog/introducing-ui-sdk) · [UI SDK core](https://ui-sdk.dev/docs/core) · [Shell dependencies](../../../deepwidgets/shell/package.json)

The React adapter requires React and React DOM 19 or later. deepWidgets pins its shell and widget-kit to 18.3.1, and the kit links authored pages to the app's copy. A second React copy has already caused problems with authored pages. Test `@ui-sdk/core` and its testing helpers first, or try the Web Components adapter behind one deepWidgets wrapper if core would require recreating too much component logic. A React adapter rollout would require a coordinated compatibility decision for the shell, the widget-kit, and installed custom pages. [Vercel React requirements](https://ui-sdk.dev/docs/react/installation) · [Core test tools](https://ui-sdk.dev/docs/core/testing) · [Web Components adapter](https://ui-sdk.dev/docs/web-components/installation) · [Kit React decision](../../specs/kit.md#decisions-kitdecisions) · [Widget-kit dependencies](../../../deepwidgets/widget-kit/package.json)

The optional UI SDK agent bridge observes registered page controls and invokes their interactions. Its observation rules and action checks are local to the page, and a rejected step can leave earlier steps applied. Test control behavior independently of that bridge. The deepWidgets connector needs device-owned grants, access to the same named widget actions when the renderer is closed, and durable operation outcomes. Keep that route through the PC's MCP endpoint and host action service. A renderer's confirmation label may describe a request. The desktop owns presenting and recording the operator's decision. [Vercel agent permissions](https://ui-sdk.dev/docs/agents/connect-an-agent/permissions) · [Vercel WebMCP bridge](https://ui-sdk.dev/docs/agents/connect-an-agent/webmcp) · [Ephemeral surface design](ephemeral-surface-design.md)

## First comparison

Record the shared interaction expectations with the existing Grocery checkbox. For the SDK comparison, use one control with a reproducible deficiency. A menu for selecting Timer presets is a suitable candidate if it exposes a focus or keyboard problem in a small floating window. Build the existing-primitive version and the SDK candidate behind the same deepWidgets props and operation binding. If both meet the expectations with comparable maintenance costs, keep the existing primitive.

- Exercise mouse, keyboard, a screen reader, visible focus, and focus restoration in a small packaged macOS window. Include light and dark mode, reduced motion, and IME input if the control accepts text.
- Run the control in both the default shell and an authored page. Check the packaged app and an offline page install with the existing content policy. Compare bundle size and cold window startup against the baseline and verify one React instance.
- Check that opening, dismissing, and retrying leave action state and focus where the operator expects. Confirm that a lost response cannot produce a false success and that an update through MCP appears through the same state refresh. Measure any change in control behavior independently of remote permission integration.
- Adopt a component only if it closes an observed gap or removes substantial maintenance while passing the same checks. Keep CSS entry points, underlying libraries, and adapter versions out of the widget-facing API.

This assessment uses the SDK documentation and the current widget architecture. Compatibility with a packaged renderer and any behavior or performance improvement still require the comparison above.
