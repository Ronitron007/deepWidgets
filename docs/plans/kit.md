# Plan for the widget kit `kit.plan`

This plan implements `docs/specs/kit.md`. The process is `widget_mvp.plan.process`.

## Units `kit.plan.units`

| Unit | Change | Check | Mutant that must fail the check | Needs |
|---|---|---|---|---|
| `kit.service` | `kit.folder`, `kit.settings`, `kit.service`, `kit.gates` | The typecheck and the lint pass. A new script `tools/kit-service.mjs` runs with a host and checks these steps. The first start makes kit version 1 with the 8 core links, and `read()` lists no extra. `add('date-fns@^4')` makes version 2 with an exact version, and a page bundle that imports `date-fns` installs. `add` of a core package gives `in-core`. With `{ "kit": { "refuseBuilds": ["core-js"] } }`, `add('core-js')` gives `install-failed` and names `core-js`. With an empty list, the install script of `core-js` runs. Exactly one `react` is in the kit, and it is the folder of the app. After the check points `core/react` at another real folder, an offline frozen install still passes. With the registry set to an address that does not answer, a page install still passes. With no store and no `node_modules`, the host starts, a page install gives `kit-unavailable` in at most 5 s, and a bundle with no `page/` installs. Two `add` calls at once give versions 2 and 3, with both extras. Two processes that change the kit at once both finish, one after the other, and `current` points at a whole version. A start during a change of another process leaves that change whole. With pnpm 10, a start gives `kit-unavailable` and names the version. After the step that writes the exact version, with `node_modules` there, exactly one `react` is in the kit. An install of the same page sources after a kit change builds the page again. While another process holds the kit lock, a page install gives `kit-unavailable` in at most 5 s, and a later install with no `page/` applies. `widgets-create`, `widgets-mcp`, `widgets-install-replay`, `widgets-action-replay`, and `widgets-crash-replay` pass. | Remove the `overrides` of the core links: the kit gets a second `react` from npm after `add('recharts')`, and the check fails. | `library.guide` |
| `kit.pane` | `kit.pane` | The typecheck and the lint pass. `tools/widgets-main.mjs` checks these steps with a host and a temp `DSH_HOME`. The answer of `settings` has the part `kit`, with the status `ready`, the kit version, the 8 core packages, and no extra. `kitAdd({ spec: 'date-fns@^4' })` answers `started` in at most 1 s. Then the status is `changing`, and later `ready`, with `date-fns` as an extra and the last change without error. `kitAdd` of a core package answers `in-core` at once. A second `kitAdd` while a change runs answers `kit-busy`. `setRefuseBuilds({ names: ['core-js'] })` writes `kit.refuseBuilds` and keeps the key `modes` of the settings file. Then `kitAdd({ spec: 'core-js' })` ends with a last change that has `install-failed` and names `core-js`. `kitRemove({ name: 'date-fns' })` removes the extra. A bad name gives `bad-name`. `DSH_SMOKE_MAIN=1` passes: the Settings tab shows the section "Widget kit" with the 8 core rows. Through the page, an add of `date-fns@^4` makes its row show, and Remove takes it away. The smoke saves `settings-kit.png`. `kit-service`, `widgets-mcp`, `widgets-install-replay`, `widgets-action-replay`, and `widgets-crash-replay` pass. | `kitAdd` waits for the end of the change: the answer takes longer than 1 s, and the check fails. | `kit.service` |
